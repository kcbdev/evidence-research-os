# PBI-065: Libraries UI (skills / prompts / roles / tools pages)

## Directive

Build the four plain-CRUD library pages the canvas depends on — no
canvas, no React Flow in this PBI. Routes: `/settings/skills` (Card
grid: name, description, using-roles + editor with Name/description
and `@uiw/react-md-editor` body; assigned-roles shown read-only —
assignment lives in the Role editor), `/settings/prompts` (Table:
name, description, last-edited, used-by-count + editor with generous
Textarea and per-save version history in an Accordion with
Revert-per-entry), `/settings/roles` (Card grid with referencing-
methodology badges + Dialog editor: Name/ID, Description, system
prompt as Prompts-library Combobox OR inline Textarea with "Save as
reusable prompt" Checkbox, Tools Checkbox grid, searchable Model
combobox reusing the `ModelSelector` pattern, output-schema Select,
Skills multi-combobox), `/settings/tools` (read-only Table: name,
description, source MCP server, with header text stating new tools
are a backend/MCP concern). All pages use `react-hook-form + zod`
(client schemas mirroring the PBI-063 Pydantic models), native
`fetch` against `/api/v1` via `lib/api.ts` (new exported functions
only — this PBI owns the `api.ts` library-section additions),
shadcn composition rules from the control-panel-ux spec (semantic
tokens, `cn()`, titled Dialogs), and RTL tests per page. Honor the
"one source of truth" relationship: role↔skill assignment is editable
only from the Role editor side.

## Verification

- Spec contracts: each page CRUDs against the real backend (seed one
  entry per library, reload, entry persists; prompt re-save creates a
  version and Revert restores it); tools page has no create/edit
  affordance; role editor's inline-prompt Checkbox promotes to the
  Prompts library in the same action.
- Executable: `cmd /c "npm.cmd --prefix frontend run typecheck"`,
  `cmd /c "npm.cmd --prefix frontend test"`, `next build` green.
