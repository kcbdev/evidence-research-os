# PBI-011: Council pass + extraction + conflict + targeted loop

## Directive

Implement the graph's convergent core in `nodes.py` per guide §2.3:
`independent_first_pass` (Scientist/Investigator/Skeptic run
concurrently with fresh context each — assert no shared input beyond
the question; budget += 3), `evidence_extraction` (findings →
`evidence/*.yaml` via the store), `conflict_detection` (populate
`open_contradictions` + `tasks/*.yaml`), `targeted_research`
(single-agent dispatch per task, `rounds_used` += 1, loop back to
conflict detection). Agent LLM calls mocked at the client boundary;
assert concurrency structure and store writes, not model output. Concurrency
risk (from PBI-004 review): simultaneous `_commit`s on one project can
interleave `index.add`/`commit` — serialize store writes per project
(or add file locking) in this PBI; concurrent in-memory reasoning is
fine, concurrent git index access is not.

  (`targeted_research` with `rounds_used` at max) terminates at

  `consume_calls`/`consume_round` (no free calls — assert increments);
  `max_sources` / `max_sources_per_claim` enforced on investigator
  dispatch. Concurrent-loop nodes return partial updates, never mutated
  full state (parallel-branch lost-update risk; sync classifier/plan are
  exempt — no parallel graph branches). `session_id` field added to
  state (PBI-014 mints it as `run_id`); these nodes make no fetch calls
  (LLM boundary only), so session readers + runtime MCP `cached_*`
  wiring are an OPEN plan-delta backlog item, not this PBI — the
  raw-fetch ban test guards the boundary meanwhile.
