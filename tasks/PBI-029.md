# PBI-029: Persist runs (history survives restarts)

## Directive

Live-fire (PBI-019): every backend restart wipes the in-memory run
registry — runs vanish from history, in-flight runs die silently,
and checkpoint rows orphan. The runs tab, the run view, and user
trust all assume runs persist. Design (not prescribed — propose in
the PBI): persist run records (id, project, status, events, error,
timestamps) to SQLite (one `runs.db` beside projects? per-project?),
rebuild in-memory handles (graphs recompile from path) on demand,
and mark runs that were `running` at startup as `interrupted`
(they cannot resume: threads don't survive processes — say so
honestly in the UI). Keep the SSE/event contract byte-identical so
the frontend does not change. Tests: registry round-trip, restart
simulation (drop memory, rehydrate, history lists; running →
interrupted), corrupted-row tolerance.

## Context

- Spec: `specs/phase-1-mvp/spec.md` (run lifecycle contracts)
- Depends on: PBI-014 (registry lives there)
- Files/modules touched: `backend/app/api/runs.py`, backend tests
  (new persistence module welcome if cleaner than inline)
- Plane: `kcb/EVRSH-29`

## Verification

- Simulated-restart tests as directed; full backend gates green;
  manual: restart backend mid-list, history intact, genuinely
  interrupted run honestly labeled.

## Refinement rule

- If reality diverges from the spec: stop, flag for human review.
  Do NOT silently resume interrupted runs (threads are gone; only
  checkpoint state persists, and resuming from it is a separate,
  harder PBI).
