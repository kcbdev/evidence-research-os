# PBI-063: Library store + API (skills, prompts, roles, tools, condition-fields, validate)

## Directive

Build the backend the builder libraries need, mirroring the existing
`app/store/methodology.py` + `app/api/methodologies.py` pattern (new
files only — do not refactor the methodology store). Deliver: Skills
CRUD (`GET/POST /skills`, `GET/PUT /skills/{id}`), Prompts CRUD
(`GET/POST /prompts`, `GET /prompts/{id}`) where POST-to-existing-id
creates a new version plus `GET /prompts/{id}/versions` history,
Custom Roles library CRUD (`GET/POST /roles`, `GET/PUT /roles/{id}`),
read-only Tools registry (`GET /tools`, reflecting backend MCP tool
config — no create/edit surface), `GET
/methodologies/condition-fields` (condition-eligible state fields as
`[{"field", "type"}]`, types at least `count` and `bool`), and `POST
/methodologies/{id}/validate` (full save validation incl. unknown
refs, orphaned loop targets, judge/council overlap — without
persisting anything). Every write validates against Pydantic schemas
with 422s naming the offending field, same fail-closed style as the
methodology API. No frontend changes in this PBI.

## Verification

- Spec contracts: CRUD round-trips persist; prompt POST-to-existing-id
  appends a version retrievable from `/versions`; `GET /tools`
  exposes no write method (405/404 on POST); `condition-fields`
  returns typed field list; `/validate` returns the same errors as
  save-validation on a bad payload and changes nothing on disk
  (re-GET shows prior state untouched).
- Executable: both backend halves green from `backend/` —
  `uv run pytest tests/ -q --ignore=tests/test_api_runs.py` and
  `uv run pytest tests/test_api_runs.py -q`.
